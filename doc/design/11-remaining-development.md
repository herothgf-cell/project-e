# 남은 개발 사항과 추천 순서

- 정리일: 2026-10-26, Asia/Seoul.
- 구현 기준: [a72f5b2](https://github.com/herothgf-cell/project-e/commit/a72f5b2984d026f2a8eff209bbc6c43464efb6f7)의 소스·기획·실행 기록 대조.
- 목적: 현재 완성 범위, 남은 기능, 검증할 가설, 다음 작업의 완료 기준을 한곳에서 관리한다.
- 전체 진행 순서는 **추천안**이며 작업량이나 출시일을 확정한 계획은 아니다. 다만 2026-10-26 사용자 요청으로 R24–R27은 **바로 다음 개발 범위에 포함**한다. 세부 제안값과 확인이 필요한 선택은 아래에서 구분한다. 미완료 체크박스는 실제 구현과 완료 증거가 갖춰졌을 때 갱신한다.

## 1. 현재 도달한 단계

**맵 1개와 세 영웅으로 오프라인 3대3 한 판이 진행되는 프로토타입**이다. 전투·성장·공성·승패의 연결은 구현되어 있다. 사람의 조작감·게임성, 독립 Windows 빌드, 온라인 대전과 출시 품질은 별도 확인이 필요하다.

|---|---|---|
| 전장과 경기 | M01 세 라인, 병력, 탑 12개·핵 2개, 승패·재시작 | 사람의 길찾기·지원·공성 사용성, 경기 흐름 검증 |

기존 검증은 5개 묶음의 **2,192개 assertion 통과**, 메인 장면 시작, 실제 렌더 8프레임이다. 6봇 일반 경기는 **20분 11초에 실제 핵 파괴로 종료**했다. 이는 한 조건의 자동 경기 결과다. 사람 1명+봇 5명과 사람 6명의 경기 시간·재미까지 검증한 결과는 아니다. 근거는 [검증 기록](09-verification.md)과 원문 로그에 있다.

이미 수정한 예약 명령 교체, 네마 지속 연결, 리오 회수점·귀환 경로, 적 선 효과의 시야 제한은 새 미구현 목록에 다시 넣지 않는다. 현재 1m 길찾기 격자는 구현 방식의 한계이며, 확인하지 않은 모든 경로를 결함으로 분류하지 않는다. 근거: [구현 차이](10-differences.md).

## 2. 바로 다음 개발 묶음 — 사람이 직접 시험할 수 있는 버전

다음 한 묶음의 목표는 **게임을 내려받아 실행하고, 자신의 조작과 전투 결과를 이해하면서 한 판을 끝내는 것**이다. 최근 Godot 실행 파일을 찾는 과정의 불편도 고려해 독립 Windows 테스트 빌드를 우선 배치한다.

### 2.1 R24 — 경험치 셀 다양화 초안

현재 셀은 6개이며 각각 HP 180, XP 30, 기본 크레딧 10이다. 첫 생성은 30초, 파괴 후 재생성은 45초다. 처치 팀의 살아 있는 영웅 중 사망 위치 14m 안에 있는 인원에게 기본 보상을 균등 분배하며 셀 막타 보너스는 없다. 현재 근거: [맵](02-map-m01.md), [유닛](04-units-and-ai.md), [성장·보상](05-growth-and-economy.md).

**제안:** 경험치량을 소형·중형·대형 세 종류로 나누고, 기존 여섯 자리에 각 종류를 두 개씩 배치한다. 이름과 수치는 기획 초안이며 확정 밸런스가 아니다.

| 제안 종류 | 셀 1개 XP | 제안 개수 | 여섯 셀을 한 번씩 파괴했을 때의 합계 기여 |
|---|---:|---:|---:|
| 소형 | 20 | 2 | 40 |
| 중형 | 30 | 2 | 60 |
| 대형 | 40 | 2 | 80 |
| 합계 | — | 6 | 180 |

이 조합은 한 번씩 파괴했을 때의 총 XP를 기존 `6 × 30 = 180`으로 유지하면서 어떤 셀을 취할지 선택을 만든다. 실제 경기의 분당 XP는 처치·재생성 빈도에 따라 달라지므로 총합 유지만으로 성장 속도가 같다고 판단하지 않는다. 기존 M01의 **180도 회전 대칭**에 대응하는 위치에는 같은 등급을 놓고, 각 진영 쪽에 각 종류를 하나씩 배치하는 안을 먼저 비교한다. 예를 들어 북서↔남동 40, 중앙 서↔중앙 동 30, 북동↔남서 20이면 양쪽 합계는 각각 90 XP다. 이 배치도 확정안이 아니며 접근 시간·지원 위험과 함께 비교한다.

초기 비교에서는 HP·크레딧·첫 생성·재생성 시간·공유 반경을 기존값으로 두는 안을 사용한다. XP 다양화와 처치 난이도 조정을 동시에 섞지 않고, 더 강한 셀이나 새로운 위치가 필요하면 이유를 별도 기록한다. 크기·형태와 XP 숫자로 종류를 구별하며 색상만으로 구분하지 않는다. 비관측 셀의 생존/재생성 변화는 시야 규칙 밖으로 노출하지 않는다.

완료 증거에는 종류별 생성/재생성, 1·2·3인 보상 공유, 부적격 수령자 제외, 중복 지급 방지, 실제 표시와 보상 일치가 포함된다. 첫 R 해금·첫 레벨 차이와 라인 이탈 비용은 R05에서 관찰한다.

### 2.2 R25 — 시야 다양화의 적용 방식

현재도 시야 규칙은 있다. 영웅과 살아 있는 구조물은 12m, 라인 병력은 8m를 제공하고 팀이 공유한다. 여섯 사각 차단체는 시야와 이동을 막으며, 셀·네마 핀·리오 회수점은 시야를 제공하지 않는다. 보이는 적과 숨은 적의 표시·선택을 구분하는 구현 위에 다양화를 추가한다. 근거: [전장의 시야 규격](02-map-m01.md), [경기 상태의 시야 판정](../../game/project-e/scripts/battle/battle_state.gd).

사용자 표현인 **‘시야 있고 없고 다양화’의 적용 단위는 아직 미확정**이다. 다음 두 안을 같은 요청으로 간주해 모두 구현하지 않고, 의도에 맞는 범위를 선택한다.

| 해석 | 기획·구현 범위 | 결정해야 할 내용 |
|---|---|---|
| 전장 구역·시야 제공원의 다양화 | 개방된 장소와 벽/은폐에 의해 관측되지 않는 장소, 또는 오브젝트의 시야 제공 여부에 차이를 만들어 지원·매복·퇴각의 선택을 늘린다. | 지형 차폐와 시야 제공원 중 요청 대상, 별도 은폐 구역 필요성, 진입/이탈·공격 시 공개 규칙, 시야를 받는 팀·반경·지속 시간 |
| 경기 시야 모드의 다양화 | 현재 팀 시야 제한 모드와 전체 시야 모드를 경기 시작 설정으로 제공한다. | 일반/기술 체험 중 어디에 제공할지, 기본값과 봇 정보 범위, 경기 중 변경 허용 여부 |

모드 방식으로 정하면 현재 팀 시야를 기본으로 유지하고 전체 시야는 시험용 선택으로 시작하는 안을 제안한다. 전체 시야에서도 벽의 이동·공격 차단은 따로 유지하며, 시야를 켰다는 이유로 벽을 관통하는 공격을 허용하지 않는다. 구역 방식이면 관측/비관측 경계와 진입·이탈 결과를 먼저 작은 장면에서 확인한다. 셀 등 오브젝트에 시야를 추가하는 방식이라면 현재의 ‘셀은 시야를 제공하지 않는다’를 바꾸는 별도 설계 결정으로 남기고 R24의 XP 변경과 구별한다.

두 방식의 공통 완료 기준은 같은 관측 결과를 화면·HP/상태·클릭·A 자동 표적·미니맵·효과·봇 판단에 적용해 숨은 적의 최신 위치를 이용하거나 노출하지 않는 것이다. 이미 발사한 기본 공격 투사체의 내부 추적은 [기존 공격 계약](03-combat.md)을 유지하되, 시야 밖 추적 구간과 숨은 적중 피드백은 표시하지 않는다. 경계 진입/이탈, 시야 제공자의 사망과 구조물 파괴, 겹친 제공원, 벽 뒤 표적을 확인한다. 선택한 시야 규칙은 R12/R13의 상태 전송 기준에도 이어받는다.

### 2.3 R26 — 방어 포탑 사거리 조정 초안

현재 포탑 공격 사거리는 **9.0m**이며 공격자 중심부터 표적 외곽까지 잰다. 원피해 180, 공격 간격 1초와 별개인 값이다. 공성의 병력 부재 보호를 해제하는 **12m는 중심 간 거리**이며 다른 규칙이다. 근거: [방어탑](04-units-and-ai.md), [거리·공성](03-combat.md), [탑 상태 생성](../../game/project-e/scripts/battle/battle_state.gd).

요청에는 늘릴지 줄일지 명시되지 않았다. 접근·퇴각의 여유를 조금 늘리는 방향이라면 **9.0→8.5m**를 첫 비교안으로 제안한다. 이 값은 약 5.6% 축소한 실험안이며 적용 확정값이 아니다. 방어 구역을 넓히려는 의도라면 증가 방향으로 비교값을 다시 잡는다.

초기 비교는 외곽·내곽에 같은 값을 사용하고 HP·피해·공격 간격·영웅 우선 공격 시간·공성 보호 반경을 유지하는 안으로 한 변수를 분리한다. 실제 공격 거리, 아군 영웅 피격에 대한 보복 어그로 감지, 보이는 범위 안내, 봇의 탑 위험 판단이 공통 사거리와 필요한 여유값을 참조하게 한다. 현재 실제 공격/보복 감지의 9.0m, 봇 위험 판단의 9.5m와 병력 없는 전진 제한 11.0m를 함께 대조해 남은 고정값을 확인한다. 근거: [보복 판정](../../game/project-e/scripts/battle/battle_rules.gd), [봇 위험 판단](../../game/project-e/scripts/battle/battle_ai.gd). 다른 대상 반경, 시야/벽 차단, 사거리 진입/이탈, 원거리 영웅의 일방 공격 가능 여부, 병력을 동반한 공성의 변화를 확인한다. 발사 후 이미 진행 중인 투사체 처리는 기존 공격 계약을 따른다.

### 2.4 R27 — A 공격 이동의 동작 기준

**확정된 요청:** `A`를 누르고 땅을 클릭하면 그 위치로 공격 이동하며 기본 공격을 진행한다. 현재 코드에는 A 공격 이동 명령이 없고, 우클릭 이동과 직접 대상 공격만 있다. 현재 입력·명령 근거: [전장 입력](../../game/project-e/scripts/presentation/battlefield.gd), [경기 명령](../../game/project-e/scripts/battle/battle_state.gd).

구현 초안:

1. A를 누르면 공격 이동 조준 상태와 커서/안내를 표시한다. 이때는 실제 이동 명령을 바꾸지 않는다. 전장 지면 좌클릭으로 목적지를 확정한다.
2. 목적지로 이동하는 동안 보이는 살아 있는 합법 표적을 탐색한다. 기본 공격의 사거리·준비 시간·공격 간격·벽·제어 상태를 그대로 적용하며 Q/W/E/R을 자동으로 사용하지 않는다.
3. 표적과 교전하는 동안 원래 이동 목적지를 보존한다. 표적 사망·잠금·시야 상실·추적 한도 초과로 교전을 끝내면 다시 유효 표적을 찾거나 목적지로 이동을 이어간다. 숨은 적의 최신 위치를 읽어 쫓지 않는다. 직접 대상 공격의 마지막 관측 후 최대 1초 유지 정책을 공격 이동에도 적용할지는 별도 결정으로 남긴다.
4. 유효한 표적을 불필요하게 매 틱 바꾸지 않는다. 목적지 도달 후에는 추가 추적 이동 없이 사거리 안의 유효 표적만 기본 공격하는 안을 사용한다. 표적 검색 반경·추적 한도는 어느 위치를 기준으로 재는지까지 근접/원거리 재현 장면에서 정해 기록한다. 팀 공유 시야 전체를 자동 탐색 거리로 쓰지 않는다.
5. 준비 중 Esc는 공격 이동 조준을 취소한다. 우클릭·S·B·새로 확정한 기술은 기존 명령 승인/예약/중단 규칙에 맞춰 최신 유효 명령으로 교체하며 이전 목적지가 나중에 되살아나지 않게 한다. 기술 준비·돌진·후딜에는 예약 하나만 유지한다. 거부된 입력은 기존 유효 명령을 임의로 지우지 않으며, 기본 공격 준비를 취소해도 공격 간격을 초기화하지 않는다.
6. 성장·일시정지·결과 화면, UI 버튼 위 클릭, 텍스트 입력 포커스와 사망 상태에서 전장 명령이 새어 나가지 않는다. 기술 조준과 공격 이동 조준은 동시에 활성화하지 않는다.

R01과 함께 표적 후보의 생존·진영·가시성·잠금 검증을 공통 규칙으로 정리한다. R01의 클릭 우선순위는 특정 지점을 직접 가리킨 상황의 규칙이다. 자동 공격 이동이 중립 셀까지 공격해 멈추는지, 이동 경로 옆의 핀을 우선 정리하는지는 별도 결정이므로 클릭 후보 전체를 무조건 자동 표적으로 복사하지 않는다. **첫 제안은 적 영웅·병력·공격 가능한 적 구조물을 자동 후보로 삼아 가까운 표적을 획득하고, 중립 셀·핀은 직접 우클릭 공격으로 남기는 것**이다. 거리 동률은 안정적인 ID 순서를 제안한다. 공격 이동 목적지와 교전 표적은 시뮬레이션에서 별도로 보관하고, 화면 입력에서 이동/공격 명령을 매번 덮어쓰는 방식에 의존하지 않는다.

완료 증거에는 A만 누른 상태, 빈 지면 이동, 이동 중 교전, 교전 후 목적지 복귀, 도착 후 비추격, 숨은 적/잠긴 탑 제외, 벽과 물가 경로, 명령 교체·기술 예약·S 정지, 사망·제어·경기 종료·재시작, UI 클릭 차단, 세 영웅별 실제 조작이 포함된다. 사람의 A 명령 구현을 영웅 봇 전술 전체 완성으로 계산하지 않는다.

### 2.5 이번 묶음 안의 진행 순서

먼저 셀 종류·배치 초안, 시야의 적용 방식, 포탑 조정 방향을 정리한다. 구현은 **R01+R27의 표적/입력 → R24 셀 보상 → R25 시야 → R26 포탑 비교**를 기본 순서로 제안하되, R25에서 정한 시야 규칙으로 R27을 다시 확인한다. R02의 벽 경고 보완과 R03의 Windows 패키지 준비는 가능한 범위에서 함께 진행한다. 마지막에 R04 안내를 실제 동작과 맞추고 R05 사람 경기에서 새 네 항목을 함께 관찰한다.

시야 방식과 포탑 방향의 확인이 남았다고 해서 R01/R02/R03 및 A 입력/명령 경계 정리를 모두 미루지는 않는다. 반대로 제안값을 확인된 사용자 선택으로 기록하거나, 문서 추가만으로 R24–R27을 완료 표시하지 않는다.

경기 시간 목표의 기준은 [사람 6인 정상 경기의 중앙값 12–18분](../../docs/04-playtest-and-balance.md)이라는 가설이다. 6봇 한 경기의 20:11만으로 특정 영웅을 하향하거나 핵 HP를 줄이지 않는다. 복귀·이동·부활·병력 보호 중 지연 원인을 확인하고 한 번에 바꾸는 변수를 제한한다. 현재 각 팀에 세 영웅이 모두 들어가므로 영웅 승률만으로 균형을 판단하기도 어렵다.

| R12 | 2클라이언트 서버 판정 진단 | 작은 장면에서 바스 이동·기본 공격·E부터 시작하고 나머지 판정으로 확장 | 두 독립 실행 클라이언트가 같은 서버 결과를 본다. 입력 소유권·번호·자원 검증, 상태 전송, 자기 이동의 예측/보정, 원격 유닛 보간과 중복 효과 방지를 확인한다. RTT 50/100/150ms·손실 조건과 호스트 역할 교대를 기록한다. |
| R13 | 전체 3라인·3영웅·6클라이언트 동기화 | R12 통과 후 병력·구조물·장치·성장·보상·승패를 확장 | 숨은 적 상태의 전송 범위를 제한한다. 리오 왕복, 네마 핀 제거, 사망/부활, 동시 핵 파괴가 일치하며 중복 피해/소비/보상이 없다. 현재 팀0 고정 표시를 실제 조작 팀 기준으로 일반화한다. |
| R14 | 비공개 방과 온라인 경기 흐름 | 생성/참가→팀/영웅 선택→준비→시작→결과→재경기 | 버전 차이·가득 찬 방·참가 실패·호스트 종료를 구별한다. 온라인 성장 패널은 경기 전체를 멈추지 않게 설계한다. 팀 상태와 지원/공격/후퇴 핑도 실제 전송 규칙과 연결한다. |
| R15 | 연결 손실·봇 인계·재접속 | 문서의 5초 인계/60초 복귀는 초기 정책 | 한 영웅을 사람과 봇이 동시에 제어하지 않는다. HP·쿨타임·성장·부활 시각을 복원한다. 호스트 종료는 세션 중단으로 안내하고 승패를 만들어내지 않는다. |

현재 구현은 로컬 시뮬레이션이다. 규칙과 표시를 분리했다는 사실만으로 전송·예측·보정이 구현된 것은 아니다. 네트워크 기술 선택과 자세한 계약은 [기존 아키텍처 계획](../../docs/technical/02-architecture-and-networking.md)을 따른다. ENet/RPC 직접 연결 진단과 Steam 초대/전송 경로는 각각 검증한다.

초기 조사값인 입력 반응·이동 보정 거리·30Hz 서버 주기와 이후 60fps 목표를 이미 달성한 성능으로 쓰지 않는다. 실제 6인 경기를 확보한 뒤 세 라인의 지원·성장·공성, 진영과 조합의 영향을 다시 평가한다.

## 7. 검증 후 결정할 확장

현재의 재미 목표는 **짧은 기술 교환, 세 라인 사이의 지원 판단, 경기 중 성장, 병력을 동반한 공성**이다. 콘텐츠 수를 늘리는 것만으로 이 네 가지를 검증했다고 판단하지 않는다.

## 8. 추천 진행 순서와 단계 종료 기준

| 단계 | 주된 작업 | 함께 준비할 일 | 다음 단계로 넘어갈 근거 |
|---|---|---|---|
| 1. 직접 시험할 수 있는 로컬판 | R01–R05와 사용자 요청 R24–R27 | 빌드 식별·기본 로그·첫 PC 성능 기록 | 셀·시야·포탑·A 입력의 구현/검증 근거를 남기고, Windows에서 일반 경기와 재시작을 완료해 실제 플레이 문제 목록을 확보 |
| 2. 선택과 반응 개선 | R06–R11 중 관측상 우선 과제 | R12의 작은 2클라이언트 진단 | 조작/기술/성장/공성 이유를 설명할 수 있고, 온라인 기본 판정/보정 위험을 확인 |
| 3. 실제 사람 6인 경기 | R13–R15와 균형 재검증 | 검증된 한 영웅/맵 구역의 아트·핵심 소리 | 접속→한 판→결과→재경기가 이어지고 지원·성장·공성에 선택 이유가 나타남 |
| 4. 외부 테스트와 출시 품질 | R16–R23 중 확정한 제품 범위 | 필요성이 확인된 영웅 한 종씩 확장 | 실제 배포/업데이트·지원 PC·운영 방식과 공개 기능이 검증된 출시 후보 |

기간은 각 작업의 실제 소요와 재작업, 주당 가용 시간, 외부 테스트 모집/검수 대기를 기록한 뒤 추정한다. 한 사람의 여러 역할을 병렬 인원 수로 계산하지 않는다.

## 9. 작업 완료 기록 양식

각 항목을 완료 처리할 때 ID, 변경 이유, 구현 commit, 사용 빌드, 자동 검사와 사람/Windows/온라인 확인 결과, 남은 한계를 함께 남긴다. 코드가 들어간 것과 사람이 확인한 결과를 별도 상태로 기록한다.

이번 정리는 문서와 소스의 읽기 대조다. 게임 기능이나 전투 수치를 변경하지 않았으며, 위 2,192개 검사와 봇 경기 결과는 기준 구현의 [기존 실행 증거](09-verification.md)를 인용했다. 이후 변경에는 그 변경의 위험을 확인할 검사와 실제 플레이 증거를 추가한다.
