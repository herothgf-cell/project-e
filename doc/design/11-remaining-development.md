### 2.1 R24 — 현재 셀 종류와 배치

| 종류 | 1개 XP | 자리 | 개수 |
|---|---:|---|---:|
| 소형 | 20 | 북동 `(18,24)` ↔ 남서 `(-18,-24)` | 2 |
| 중형 | 30 | 중앙 서 `(-24,6)` ↔ 중앙 동 `(24,-6)` | 2 |
| 대형 | 40 | 북서 `(-18,24)` ↔ 남동 `(18,-24)` | 2 |

총량은 한 번씩 파괴했을 때 **180 XP**, 진영 쪽별로 **90 XP**다. 기존 `6×30`과 합계는 같지만 처치·재생성 빈도와 라인 이탈에 따라 실제 성장 속도는 달라질 수 있다. 이 값은 사용자의 다양화 요청에 따른 첫 구현값이며 최종 밸런스가 아니다.

HP180·물리 반경0.55m·크레딧10·첫 생성30초·재생성45초·처치 팀 생존 영웅14m 공유를 유지한다. 크리스털 1/2/3개와 높이, 보이는 셀의20/30/40 XP 숫자로 구별한다. 숨은 셀의 생존·재생성·HP는 노출하지 않는다. [맵](02-map-m01.md), [유닛](04-units-and-ai.md), [보상](05-growth-and-economy.md)에 현행 규칙을 기록했다.

### 2.2 R25 — 현재 시야 표현과 한계

영웅·살아 있는 아군 탑/핵12m, 병력8m, 여섯 벽 차단의 팀 공유 규칙을 유지한다. 셀·핀·회수점은 시야를 제공하지 않는다. 아군 제공원에는 체력바와 겹치지 않는 눈 모양 표식을 두고 마우스오버로 제공 반경과 벽에 잘린 윤곽을 보여 준다. 포탑의 호박색 점선 공격 범위와 밝은 시야 윤곽을 구별한다.

전장과 미니맵은 같은 **1m 현재 시야 마스크**를 사용한다. 관측 영역은 원래 밝기, 비관측 영역은 낮은 명도·채도다. 고정 지형과 길은 계속 읽힌다. 적 구조물 위치·파괴 정보가 공개되어 있어도 주변 시야를 주지는 않는다.

이 음영은 표시용 샘플이다. 텍셀 중심과 임의 지점 차이는 최대 약0.71m이며, 이동 갱신은250ms 간격과0.1m 이하 이동 억제를 사용한다. 제공원 사망·추가·제거는 즉시 갱신한다. 클릭·적 모델·HP·셀 숫자·자동 표적은 정확한 현재 판정으로 제한한다. Linux 진단에서68유닛/아군34제공원의 음영 갱신은 중앙값27.8ms·최대36.4ms였다. 이 갱신 비용은 실제 Windows PC의 R18 측정에 포함하며60fps를 보장하지 않는다. [UI 규격](06-ui-and-controls.md)과 [검증](09-verification.md)을 함께 본다.

### 2.3 R26 — 포탑8.5m 첫 구현

외곽·내곽 공격 사거리를 **9.0→8.5m**, 약5.6% 줄였다. 공격자 중심부터 표적 외곽까지 잰다. HP·원피해180·간격1초·영웅 우선 공격 유지 시간은 그대로다. 병력 부재 보호 해제의12m는 중심 간 거리이며 별도 규칙이다.

공격과 보복 감지가 `attack_range`를 참조하고, 봇의 위험 여유는 사거리+0.5m와 사거리+2m로 계산한다. 표시는8.5m 공격 점선과12m 시야 윤곽을 구분한다. 이미 발사한 투사체 처리는 기존 계약을 유지한다. [공통 전투](03-combat.md), [탑·AI](04-units-and-ai.md)에 변경 이유와 현행값을 기록했다.

### 2.4 R27 — 현재 A 공격 이동

1. A는 조준만 준비한다. 지면 좌클릭이 승인될 때 실제 공격 이동 명령을 넣고 목적지를 보관한다.
2. 자기 중심8m 안의 **보이는 적 영웅·병력·공격 가능한 구조물** 중 가까운 표적을 고른다. 동률은ID다. 셀·핀은 직접 우클릭 대상으로 유지한다.
3. 획득 지점에서8m까지 추격하고 시야 상실·사망·잠금·한도 초과 시 표적을 놓는다. 같은 표적을 다시 잡아 추적 한도를 초기화하지 않는다.
4. 교전 후 원래 목적지로 복귀한다. 도착 후에는 기본 공격 사거리 안에서만 공격하며 새 추격을 시작하지 않는다. 기술은 자동 사용하지 않는다.
5. Esc는 새 조준만 취소한다. S는 정지, 우클릭은 새 이동/공격으로 교체한다. 기술·예약 명령도 최신 유효 명령만 유지하고 거절된 명령은 이전 의도를 지우지 않는다. UI·도움말·사망·결과 화면은 전장 명령을 막는다.

직접 클릭은 영웅→병력→공격 가능한 구조물→셀→핀 순서다. 자동 공격 이동의 거리 기준 우선순위와 다르다. [조작](06-ui-and-controls.md), [명령 규칙](03-combat.md), [검증](09-verification.md)에 경계 사례를 남긴다.

- 키/화면: G 성장/B 기지 이동을 유지하고 P 상점/D 사용을 추가한다. 상점은 어디서나 설명을 열어 로컬 일시정지하고 직전 정지 상태로 복원한다. 구매는 경기 중 자기 기지 안의 살아 있는 영웅만 가능하다. 슬롯은 I01/I02 종류별 수량이며 클릭은 선택만 한다. 빈 선택을 유지하고 D가 다른 품목을 대신 쓰지 않는다.
- 경계: 최근 피해·공유 쿨타임 중에도 구매 가능하다. 사용은 기절/속박 중에도 허용하고 조준·이동·공격·시전·예약 명령을 보존한다. 보호막·장치·지속 피해를 포함한 유효 적 영웅 귀속 피해만 패치를 중단한다. 실패는 비용을 소비하지 않고, 승인 뒤 중단은 환급하지 않는다. 사망 시 효과만 종료하고 재고·선택을 유지하며 쿨타임은 사망 중 감소한다.
- R10 부분: 같은 권한 API로 기지에서 빈 종류를 패치 우선으로 채워 패치1개+병1개를 목표로 한다. 기지 밖 HP 부족200/최근 적 피해2초 조건에서 패치 우선, 그 외 에너지 부족40에서 병을 사용한다. 조작 영웅·비활성 봇·사망 영웅을 제외하고 기존 이동·복귀 전술을 바꾸지 않는다.

확보한 증거는 권한/실제 입력/봇 검사, 기존 회귀와 통합 실행,431.8초의 자연6봇 경기다. 720p/1080p 최종 화면 검수와 새 Windows export·패키지 결과는 [최신 검증](13-consumables-verification.md)에 별도로 확정한다. R06 전체 표현·R10 핵 방어/지원/라인 전환·R11 사람 경기 흐름·설정 저장·온라인은 이번 완료 범위에 포함하지 않는다. 상세 계약은 [경제](05-growth-and-economy.md), [UI](06-ui-and-controls.md), [AI](04-units-and-ai.md)에 기록한다.

소모품은 이미 정해 둔 [성장·경제](05-growth-and-economy.md)의 최소 범위를 사용한다. 에너지 병은 40크레딧/2초간 에너지40, 수리 패치는 50크레딧/4초간 HP200이며 적 영웅 귀속 피해로 중단된다. 합산 2개 보유와 공유 12초 사용 쿨타임, 자기 기지/생존 구매 조건을 함께 구현·검증한다. 이 과제를 장비 조합이나 계정 재화 추가로 확장하지 않는다.

경기 시간 목표의 기준은 [사람 6인 정상 경기의 중앙값 12–18분](../../docs/04-playtest-and-balance.md)이라는 가설이다. 기존6봇20:11, 소모품 추가 전27:18 동쪽 승리, 이번431.8초(약7:12) 서쪽 승리는 서로 다른 소스 조건의 관찰이다. 특히 소모품 추가 후 변화가 크므로 회복·사망·공성 압박과 구매/사용 빈도를 후속 비교하되 한 조건으로 가격·회복량·특정 영웅·핵 HP나 진영 균형을 확정하지 않는다. 복귀·이동·부활·병력 보호 중 지연 원인을 확인하고 한 번에 바꾸는 변수를 제한한다. 현재 각 팀에 세 영웅이 모두 들어가므로 영웅 승률만으로 균형을 판단하기도 어렵다.

## 4. 온라인 — 초기부터 작은 진단을 병행

**R12의 2클라이언트 진단은 R06–R11을 전부 마친 뒤까지 미루지 않는다.** Windows 실행 기반과 기본 명령 경계가 준비되면 로컬 개선과 같은 초기 개발 구간에 착수한다. 실제 작업 순서는 같은 사람이 맡는 역할과 가용 시간에 맞춘다.

| ID | 남은 작업 | 범위 | 완료 기준 / 의존성 |
|---|---|---|---|
| R12 | 2클라이언트 서버 판정 진단 | 작은 장면에서 바스 이동·기본 공격·E부터 시작하고 나머지 판정으로 확장 | 두 독립 실행 클라이언트가 같은 서버 결과를 본다. 입력 소유권·번호·자원 검증, 상태 전송, 자기 이동의 예측/보정, 원격 유닛 보간과 중복 효과 방지를 확인한다. RTT 50/100/150ms·손실 조건과 호스트 역할 교대를 기록한다. |

| R14 | 비공개 방과 온라인 경기 흐름 | 생성/참가→팀/영웅 선택→준비→시작→결과→재경기 | 버전 차이·가득 찬 방·참가 실패·호스트 종료를 구별한다. 온라인 성장 패널은 경기 전체를 멈추지 않게 설계한다. 팀 상태와 지원/공격/후퇴 핑도 실제 전송 규칙과 연결한다. |
| R15 | 연결 손실·봇 인계·재접속 | 문서의 5초 인계/60초 복귀는 초기 정책 | 한 영웅을 사람과 봇이 동시에 제어하지 않는다. HP·쿨타임·성장·부활 시각을 복원한다. 호스트 종료는 세션 중단으로 안내하고 승패를 만들어내지 않는다. |

현재 구현은 로컬 시뮬레이션이다. 규칙과 표시를 분리했다는 사실만으로 전송·예측·보정이 구현된 것은 아니다. 네트워크 기술 선택과 자세한 계약은 [기존 아키텍처 계획](../../docs/technical/02-architecture-and-networking.md)을 따른다. ENet/RPC 직접 연결 진단과 Steam 초대/전송 경로는 각각 검증한다.

초기 조사값인 입력 반응·이동 보정 거리·30Hz 서버 주기와 이후 60fps 목표를 이미 달성한 성능으로 쓰지 않는다. 실제 6인 경기를 확보한 뒤 세 라인의 지원·성장·공성, 진영과 조합의 영향을 다시 평가한다.

|---|---|---|
| 오린·테르·무아 등 추가 영웅 | 초기 세 영웅의 실제 상대법·학습·6인 교전에서 부족한 선택을 확인 | 개념 후보다. [확장 기획](../../docs/characters/04-roster-expansion.md)에 따라 필요한 한 명부터 상세 설계한다. |
| 공개 매칭 | 지역·시간대별 실제 접속자와 경기 성립률·대기 시간·실패율 확보 | 비공개 방과 외부 테스트 뒤 제공 여부를 결정한다. |
| 두 번째 맵·랭크·스킨·배틀패스·계정 성장·다른 플랫폼 | 핵심 제품이 검증되고 별도 목표·제작 범위를 정함 | 현재 다음 개발 묶음에서 보류한다. |

현재의 재미 목표는 **짧은 기술 교환, 세 라인 사이의 지원 판단, 경기 중 성장, 병력을 동반한 공성**이다. 콘텐츠 수를 늘리는 것만으로 이 네 가지를 검증했다고 판단하지 않는다.

## 8. 추천 진행 순서와 단계 종료 기준

| 단계 | 주된 작업 | 함께 준비할 일 | 다음 단계로 넘어갈 근거 |
|---|---|---|---|
| 1. 직접 시험할 수 있는 로컬판 | R01–R05와 사용자 요청 R24–R27 | 빌드 식별·기본 로그·첫 PC 성능 기록 | 셀·시야·포탑·A 입력의 구현/검증 근거를 남기고, Windows에서 일반 경기와 재시작을 완료해 실제 플레이 문제 목록을 확보 |
| 2. 선택과 반응 개선 | 자동 검증된 R09·R10 경제 판단의 사람 확인과 R06–R11 남은 우선 과제 | R12의 작은 2클라이언트 진단 | 조작/기술/성장/공성 이유를 설명할 수 있고, 온라인 기본 판정/보정 위험을 확인 |
| 3. 실제 사람 6인 경기 | R13–R15와 균형 재검증 | 검증된 한 영웅/맵 구역의 아트·핵심 소리 | 접속→한 판→결과→재경기가 이어지고 지원·성장·공성에 선택 이유가 나타남 |
| 4. 외부 테스트와 출시 품질 | R16–R23 중 확정한 제품 범위 | 필요성이 확인된 영웅 한 종씩 확장 | 실제 배포/업데이트·지원 PC·운영 방식과 공개 기능이 검증된 출시 후보 |

기간은 각 작업의 실제 소요와 재작업, 주당 가용 시간, 외부 테스트 모집/검수 대기를 기록한 뒤 추정한다. 한 사람의 여러 역할을 병렬 인원 수로 계산하지 않는다.

## 9. 작업 완료 기록 양식

각 항목을 완료 처리할 때 ID, 변경 이유, 구현 commit, 사용 빌드, 자동 검사와 사람/Windows/온라인 확인 결과, 남은 한계를 함께 남긴다. 코드가 들어간 것과 사람이 확인한 결과를 별도 상태로 기록한다.

2026-10-27에는 이전 로컬 기능 묶음의 실제 코드·규칙·표시와 빌드 도구를 변경했고, 이어 R09·R10 경제 판단의 구현·자동 검증을 완료했다. 이전 실행 증거는 [과거 검증](09-verification.md), 이번 자동 검사·자연 경기·최종 화면·새 export 상태는 [최신 검증](13-consumables-verification.md)에 따로 남긴다. 실제 Windows PC와 사람 플레이는 수행한 결과가 생길 때만 완료 처리한다. [플레이 기록표](12-local-playtest-record.md)는 현재 미실시 양식이다.
