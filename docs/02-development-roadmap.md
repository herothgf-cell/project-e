# 개발 로드맵

- 버전/작성일: v0.1 / 2026-10-21
- 상태: 산출물과 검증 기준을 기준으로 한 계획. Unity 구현 단계는 아직 시작하지 않았다.
- 관련: [프로젝트 개요](00-project-brief.md), [콘텐츠 범위](03-content-matrix.md), [플레이테스트](04-playtest-and-balance.md), [Steam 출시](release/01-steam-release-plan.md)

## 1. 로드맵을 사용하는 방법

M0–M6는 개발 순서다. 각 단계는 정해진 날짜가 아니라 확인 가능한 결과를 통과해야 끝난다. 인원·숙련도·주당 투입 시간·예산이 확인되지 않았으므로 현재 문서에는 출시일이나 몇 개월 완성 약속을 넣지 않는다.

진행의 기준은 **전투의 반응성 → 실제 3대3 한 판 → 새 게임의 정체성과 학습 → 외부 접속과 운영 → 출시 준비**다. 예측·지연 문제를 마지막에 붙이지 않도록 첫 전투 단계에 두 클라이언트 검증을 넣는다.

| 단계 | 확인할 핵심 질문 | 필수 산출물 | 완료 상태 |
|---|---|---|---|
| M0 설계·환경 | 같은 규칙과 환경으로 개발할 수 있는가? | 기획 정본, 에디터/패키지 고정, 작업 범위 | 문서 작성; 환경 구성 대기 |
| M1 전투·온라인 진단 | 짧은 기술 교환을 지연 환경에서도 믿고 조작할 수 있는가? | C01 진단 장면, 2클라이언트 빌드, 측정 기록 | 미착수 |
| M2 한 판 완성 | 세 라인에서 성장·지원·공성이 함께 작동하는가? | M01, C01–C03, 실제 3v3, 기본 봇 | 미착수 |
| M3 비공개 알파 | 새로 배울 만한 고유한 재미가 있는가? | 6인 경기 기록, 표현 기준, 튜토리얼 | 미착수 |
| M4 외부 Playtest | 낯선 사용자가 접속하고 다시 플레이하는가? | Steam 테스트 배포, C04–C06 검증, 서버 결정 | 미착수 |
| M5 출시 후보 | 설명한 제품을 안정적으로 제공할 수 있는가? | 완성 자산, 성능/복구 증거, 스토어·빌드 제출물 | 미착수 |
| M6 출시·운영 | 운영 가능한 상태로 실제 공개할 수 있는가? | 공개 빌드, 대응 절차, 운영 관측 | 미착수 |

## 2. M0 — 설계 정본과 재현 가능한 환경

### 작업

1. [공통 규칙](01-core-rules.md), 최초 세 영웅, 맵·경제·모드 기획을 같은 버전으로 묶는다.
2. Unity 6.3 LTS 계열의 실제 사용 가능한 안정 패치와 Windows 빌드 모듈을 선택한다. 에디터 버전과 패키지 버전을 저장소에 고정한다.
3. URP, 입력, UI, 네트워크 진단 후보의 호환성을 작은 빈 프로젝트에서 확인한다. 현재 문서만으로 호환성 검증을 완료했다고 기록하지 않는다.
4. 프로젝트 폴더, 판정/표현/전송 계층, 데이터 ID, 빌드 버전 규칙을 만든다. [구조 문서](technical/02-architecture-and-networking.md)를 따른다.
5. 실제 담당 인원, 사용 장비, 주당 투입 가능 시간, 유료 도구/서버 비용 책임을 기록한다.
6. 코드·Unity `.meta` 등 추적할 파일과 `Library/`·임시 빌드 등 생성물을 구분한다. 대형 원본 자산의 버전 관리 방식은 실제 규모에 맞춰 정한다.

### 통과 기준

- 다른 개발 환경에서도 저장소를 받아 같은 버전으로 열고 Windows 빈 빌드를 실행한다.
- 기술·성장·구조물의 데이터가 문서 ID와 연결되며 어떤 문서가 정본인지 분명하다.
- M1의 작업량과 검증 장비를 정한다. 현재 완료된 것은 기획 문서이며 이 환경 검증은 후속 작업이다.

## 3. M1 — 한 영웅의 전투와 두 클라이언트

### 작업 묶음

| 작업 | 내용 | 확인할 증거 |
|---|---|---|
| M1-01 이동·입력 | 카메라, 우클릭 이동/기본 공격, 단일 행동 예약, 키 재지정 | 명령 취소·충돌·사거리 표시가 일치하는 영상 |
| M1-02 판정 | 피해, 방어, 보호막, 제어 한도, 에너지, 사망 | 경계 사례의 입력/판정 로그 |
| M1-03 C01 | 바스 패시브와 Q/W/E/R, 기술 경고, 대응 가능한 지연 | 적·아군·자신 화면에서 같은 공격을 설명 가능 |
| M1-04 성장 | 레벨/포인트 투자, R 해금, 훈련 초기화 | 잘못된 투자·중복 승인·수치 소급 방지 |
| M1-05 온라인 | 권한 서버, 두 클라이언트, 로컬 예상 표시·서버 보정 | RTT 50/100/150ms 및 손실 조건별 측정 |
| M1-06 진단 빌드 | 더미·벽·간단한 전투 구역, 재현 명령과 로그 | 실행 파일·commit·설정이 연결된 검증 기록 |

진단 장면은 한 영웅의 위험을 빨리 드러내기 위한 것이다. 한 라인에서 싸울 수 있다는 이유로 3라인 게임이 완성되었다고 판단하지 않는다. 임시 도형과 명확한 경고선을 사용하고 최종 모델 제작을 넓히지 않는다.

### 통과 또는 재설계

- 정상 입력의 로컬 반응과 서버 확정 결과를 각각 측정한다. [온라인 기준](04-playtest-and-balance.md)의 가설과 측정 환경을 함께 기록한다.
- 100ms RTT 환경에서 반복되는 위치 되감김·맞았는데 무효·자원 이중 소비가 남으면 M2의 콘텐츠 확장을 보류한다.
- 선택한 네트워크 패키지에 예측·재조정 기능이 자동으로 들어 있다고 가정하지 않는다. 후보 변경이 필요하면 이 단계에서 비교 실험한다.
- 반응성 또는 기술 상대법이 실패하면 기술 속도·범위·판정·네트워크 구조 중 원인을 구분해 수정한다.

## 4. M2 — 실제 3대3 한 판

### 제작 범위

- M01 수로 공방의 세 라인, 연결 통로, 시야 차폐, 양 팀 방어탑 12개와 공명핵 2개.
- C01 바스, C02 리오, C03 네마. 상대 팀과 같은 영웅은 허용한다.
- 근접/원거리/공성 병력, 경험치 셀 6개, 성장 포인트, 크레딧, 소모품 2종.
- 영웅 선택 → 준비 → 경기 → 사망/부활 → 핵 파괴 → 결과 → 재경기의 완전한 흐름.
- 비공개 방과 기본 봇. 사람이 부족해도 규칙 검증을 할 수 있는 구성을 제공한다.
- 5초 연결 손실의 봇 인계, 60초 복귀, 초기 호스트 종료 시 세션 중단 안내.

### 통과 기준

1. 실제 세 라인에서 3대3을 시작하고 공통 규칙에 따라 승패 또는 무승부를 확정한다.
2. 분산 파밍, 합류, 공성의 손익이 모두 발생한다. 세 명이 계속 한 덩어리로만 움직이는 해법이 지배하면 보상·이동·탑 규칙을 조정한다.
3. 리오의 귀환 궤적, 네마의 장치 파괴와 연결선이 온라인에서 일관되게 보인다.
4. 봇의 보조가 필요한 테스트와 사람 6명의 테스트를 구분해서 기록한다.
5. 핵 동시 파괴, 이중 처치, 사망 중 재접속, 시야 밖 적중 정보 등의 경계 사례를 확인한다.

진행 불가와 규칙 모순이 해결되면 M3로 간다. 영웅 수, 맵 수, 영구 계정 성장을 추가해 부족한 한 판의 재미를 덮지 않는다.

## 5. M3 — 비공개 알파와 고유한 정체성

### 작업

1. 서로 다른 숙련도를 포함한 실제 6인 세션을 운영한다. 표본 목표와 인터뷰 방법은 [검증 문서](04-playtest-and-balance.md)에 둔다.
2. 바스의 진입·회수 위험, 리오의 이동으로 궤적 만들기, 네마의 경로 통제를 각각 설명할 수 있는지 확인한다.
3. [표현 문서](content/01-world-and-presentation.md)의 실루엣·재질·경고·소리 기준을 실제 영웅 1종과 맵 한 구역에 적용한 뒤 확장한다.
4. 이동/기술/성장/지원/공성을 순서대로 배우는 훈련과 인게임 안내를 넣는다.
5. 플레이어가 설명한 재미, 합류 빈도, 성장 선택 이유, 포션 구매, 경기 길이를 확인하고 공통 수치를 갱신한다.
6. 검증된 실제 화면을 기반으로 게임 소개와 Steam 준비 목록을 구체화한다.

### 통과 기준과 콘텐츠 확장 결정

- 신규 플레이어가 왜 피해를 받았고 무엇으로 대응할 수 있는지 설명한다.
- 참고 게임을 해본 사람도 이 게임만의 기술 연계나 전장 결정을 구체적으로 지목한다.
- 6인 온라인 경기를 완주하고 다시 해볼 의사가 있는 이유를 확인한다. 친구 관계에 의한 호의적 평가는 행동 기록과 함께 해석한다.
- 위 조건이 성립한 뒤 C04–C06 중 기존 조합의 빈틈을 해결하는 후보부터 제작한다. 세 후보를 동시에 구현할 필요는 없다.

## 6. M4 — Steam Playtest와 출시 형태 결정

### 두 작업 흐름

| 게임 제작 | 배포·운영 검증 |
|---|---|
| 추가 영웅을 한 종씩 구현하고 기존 세 영웅과 대조 | Steam 설치·업데이트·초대·접속을 실제 환경에서 시험 |
| 맵 가독성·튜토리얼·봇 연습 완성도 향상 | 예약 시간대·지역별 6인 성립률과 대기 시간 측정 |
| 여섯 영웅 후보에서 조합·상대법 검증 | listen server와 전용 서버의 공정성·비용 비교 |
| 전투/성장/경제의 불필요한 복잡성 제거 | 실패 안내·재접속·신고/지원 경로 확인 |

Steam 계정·App·Playtest의 실제 실행은 해당 비용과 공개 범위를 정하는 별도 작업이다. 절차와 공식 조건은 [출시 계획](release/01-steam-release-plan.md)을 따른다.

### M4에서 반드시 남길 결정

- 출시용 온라인 구조와 지역, 월 운영 예산, 호스트/서버 장애 정책.
- 여섯 영웅 후보 중 출시 포함 대상과 미해결 조합 문제.
- 공개 매칭 제공 여부. 수요가 부족하면 예약 세션 확대 또는 비공개 방·봇 중심 제품 범위를 검토한다.
- 게임명, 유료/무료 방식, 공개 기능, 언어, 지원 경로.
- 제작 속도와 남은 작업의 실제 추정을 바탕으로 한 출시 후보 일정.

M4의 테스트 결과 없이 공개 큐·경쟁 랭크·무료 서버 운영을 확정하지 않는다.

## 7. M5 — 출시 후보

기능 추가를 줄이고 실제 제공할 제품을 고정한다. [콘텐츠 매트릭스](03-content-matrix.md)의 출시 후보 자산을 완성하고, [Steam 계획](release/01-steam-release-plan.md)의 제출물과 실제 빌드를 대조한다.

### 필수 산출물

- 최종 출시 범위, 플레이 가능한 영웅 목록, 맵, 모드, 알려진 제약.
- 검증한 최소 PC 사양, 1080p 낮음 설정의 프레임 분포, 최대 교전에서 서버 틱 측정.
- 설치/재설치/업데이트/초대/실패/복귀/종료의 회귀 기록.
- 한국어와 지원할 영어 범위, 키 재지정·색상 외 경고·오디오 설정 검수.
- 실제 게임 화면으로 만든 스토어 자료, 요구된 심사·대기 조건의 확인 기록.
- 선택 빌드, 이전 호환 빌드, 장애 대응 담당, 긴급 패치·복구 절차.

출시 차단 결함은 진행 불가, 빈번한 크래시, 재현 가능한 판정/자원 악용, 잘못된 승패, 지원 기능의 허위 표시다. 확인되지 않은 문제를 단순히 낮은 우선순위로 바꿔 출시 기준을 통과시키지 않는다.

## 8. M6 — 실제 출시와 운영

검토 가능한 빌드·가격·공개 문구·일정을 묶어 실제 출시를 결정한다. Steam 공개는 개발 문서 작성과 구분되는 실행이다.

출시 직후 우선순위는 접속과 경기 완주, 중대 결함, 판정 신뢰, 학습 장벽 순으로 둔다. 콘텐츠 추가는 기존 게임의 문제를 확인하고 고칠 시간을 침해하지 않는 범위에서 진행한다. 운영 목표·사후 분석·패치 내역은 실제 수치를 기록하고 공개 큐를 유지할 조건을 재검토한다.

## 9. 역할과 병렬 작업

| 책임 역할 | 주된 결정 | 먼저 필요한 입력 |
|---|---|---|
| 기획/플레이테스트 | 규칙·수치·인터뷰·단계 통과 | 공통 정본과 관측 로그 |
| 게임플레이 개발 | 이동·기술·성장·AI·공성 | M1 판정/데이터 계약 |
| 온라인/빌드 | 권한·전송·재접속·배포·성능 | 게임 명령과 상태의 경계 |
| 아트/애니메이션/오디오 | 식별성·전투 경고·최종 자산 | 검증된 기술 타이밍과 표현 기준 |
| 제품/운영 | 테스트 모집·스토어·비용·지원 | 실제 기능과 배포 가능한 빌드 |

한 사람이 여러 역할을 맡을 수 있다. 역할 수를 필요한 채용 인원으로 해석하지 않는다. 네트워크 계약과 기초 입력은 의존성이 크므로 선행하고, 확인된 데이터 계약 이후 영웅 표현·UI·테스트 준비를 병렬 진행한다.

## 10. 일정 추정과 범위 조정

M1에서 실제 작업 시간과 재작업 원인을 남긴다. M2부터 각 작업에 낙관/기준/보수 추정과 선행 작업을 붙인다. 단순히 모든 작업 시간을 인원으로 나누지 않고 같은 사람이 맡는 역할과 의존 경로를 반영한다.

완료 예상 범위는 `남은 작업 시간 ÷ 실제 주당 가용 시간`에 외부 심사·모집 대기와 재작업 여유를 더해 갱신한다. 인원이 바뀌거나 네트워크 후보를 교체하면 이전 날짜를 그대로 유지하지 않는다.

범위를 줄일 때 우선 보류할 것은 추가 맵, 랭크, 관전/리플레이, 외형 수집, 계정 성장, 다른 플랫폼이다. 빠른 교전, 세 라인 지원, 경기 중 성장, 공성 승리, 온라인 판정 신뢰는 핵심으로 유지한다. 영웅 여섯 종 목표를 줄이는 경우에도 새 제품 범위와 선택 다양성을 다시 검증한다.
