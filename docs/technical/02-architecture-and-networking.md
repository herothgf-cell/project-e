# 전투 아키텍처와 네트워크 검증 계획

- 상태: v0.1 설계 제안, 구현·접속·성능 시험 미실행.
- 작성·공식 출처 확인: 2026-10-21, Asia/Seoul.
- 범위: 독립 실행 PC 3v3의 권위 시뮬레이션, 지연 검증, 기술 선택 기준.
- 관련: [공통 규칙](../01-core-rules.md), [Unity 기반](01-unity-and-steam.md), [플레이테스트](../04-playtest-and-balance.md), [로드맵](../02-development-roadmap.md).

## 1. 우선 결정

서버가 이동 가능성, 피격, 피해, 상태 이상, 성장, 재화, 승패를 최종 확정한다.
클라이언트는 입력 의도를 보내고 즉각적인 조작 표현을 제공하며 서버 결과에 맞춰 보정한다.
시작 가설은 시뮬레이션 30Hz, 스냅샷 30Hz, 렌더링 60fps다.
첫 온라인 시험은 영웅 하나·진단 장면 하나·두 독립 실행 클라이언트로 수행한다.
M2의 실제 3v3 이전에 50/100/150ms RTT에서 플레이 감각을 확인한다.
작은 테스트의 성공은 6인 경기나 실제 인터넷 연결 품질의 성공으로 간주하지 않는다.

## 2. 모듈 경계

| 계층 | 책임 | 피해야 할 결합 |
| --- | --- | --- |
| Domain | 피해식, 레벨, 분배, CC 제한, 승패 규칙 | `MonoBehaviour`, Steam ID, VFX가 규칙 소유 |
| Content | 스킬·영웅·미니언·맵의 편집용 정의 | 매치 도중 원본 데이터를 직접 수정 |
| Simulation | tick, 이동, 충돌 질의, 시전 상태, 이벤트 순서 | 렌더 프레임·애니메이션 이벤트가 피해 확정 |
| Networking | 입력·스냅샷·동기화·재접속 | 클라이언트가 선언한 피해·재화 수용 |
| Presentation | 보간, 예측 화면, UI, 음향, 카메라 | 서버 없이 실제 승패를 바꾸는 연출 |
| Platform | 로그인·로비·초대·플랫폼 설정 | Steam callback이 직접 전투 상태 변경 |

편집에는 ScriptableObject를 쓸 수 있으나 매치 시작 시 검증된 값 형식 정의로 변환한다.
규칙 함수는 입력·현재 상태·명시적 시간으로 결과를 내도록 작성하고 전역 시간에 숨겨 의존하지 않는다.
Unity 공간 질의는 인터페이스 경계로 주입하되 실제 충돌 엔진까지 순수 C#이라고 주장하지 않는다.
서버·클라이언트가 같은 콘텐츠 hash와 프로토콜 버전을 사용하는지 연결 시 확인한다.
씬 객체 이름이나 화면에 표시한 캐릭터 이름을 네트워크 식별자로 쓰지 않는다.

## 3. 명령과 상태의 계약

명령에는 연결의 플레이어 식별, 증가하는 입력 번호, 기준 tick, 이동 목적지 또는 스킬 슬롯·조준점을 담는다.
서버는 소유권, 살아 있음, 시전 가능 상태, 사거리, 자원, 쿨다운, 입력 빈도를 검사한다.
NaN·무한대·지도 밖 좌표·과거 재전송·비정상 미래 tick은 정해진 오류 정책으로 거부한다.
클라이언트가 보낸 좌표를 순간이동 결과로 수용하지 않고 서버 이동 규칙으로 목적지를 향해 진행한다.
스킬 명령은 `castId`, 명중은 `castId + phaseId + targetId`로 중복 적용을 방지한다.
반복 타격 스킬만 캐릭터 정의의 pulse 번호와 최대 타격 수를 추가한다.
공격 대상을 지정하는 기술은 팀 공유 시야를 서버에서 검사한다.
안개 속 지면 시전은 허용하되 숨은 적의 피격 정보·정확한 위치를 전달하지 않는다.
HP·쿨다운·재화는 서버의 확정 상태이며 클라이언트 연출 값과 구분한다.
보상·사망·승패 이벤트는 식별자와 순서를 보존하여 재전송에도 한 번만 처리한다.

## 4. 한 tick의 처리 순서 제안

1. 입력을 수집·검증하고 서버가 정한 처리 번호를 배정한다. 시전 승인과 에너지 차감·쿨다운 개시를 원자적으로 확정하여 같은 자원을 중복 사용하지 않게 한다.
2. 확정된 시전의 선딜·이동·충돌을 계산하고 해당 tick에 발생한 유효 타격을 모은다. 시전 승인 이후 취소되어도 이미 소비한 비용은 공통 규칙에 따라 유지한다.
3. 서버 이벤트 순서로 피해·보호막·CC를 적용한다. 시전 비용을 적중 시점에 다시 소비하지 않는다.
4. 사망·파괴·경험치·재화·리스폰 예약을 처리한다.
5. 양쪽 코어의 파괴 여부를 함께 검사해 같은 tick이면 무승부로 확정한다.
6. 가시성별 상태와 이벤트를 전송하고 진단 로그에 서버 tick을 남긴다.

타격 순서와 보상 귀속은 [공통 규칙](../01-core-rules.md)의 동시 사건 정책을 따른다.
안정적인 서버 처리 순서는 디버깅 기준이며 모든 PC의 물리 계산이 완전히 같다는 보장은 아니다.
XP·크레딧 분배의 소수는 내부에 유지하고 UI 표시에만 별도의 반올림을 적용한다.

## 5. 네트워크 후보와 M1 결정

| 후보 | 기대하는 이점 | 반드시 증명할 항목 | 판정 |
| --- | --- | --- | --- |
| A. NGO + Unity Transport + 필요한 보정 계층 | GameObject 제작 흐름으로 진단 범위를 작게 유지 | 로컬 이동 예측, 승인 입력 번호, 복원·재실행, 중복 VFX 억제 | 최초 실험의 잠정안 |
| B. Netcode for Entities | 공식적인 예측·서버 상태 복원·재시뮬레이션 모델 | ECS 제작 비용, 스킬·충돌 변환, 재시뮬레이션 CPU 비용 | A가 기준 미달이거나 비용이 커지면 비교 |

NGO 3.1 문서는 client anticipation이 완전한 client prediction/reconciliation·rollback-and-replay를 제공하지 않는다고 설명한다. [N1]
따라서 `NetworkTransform`과 보간만 붙인 결과를 빠른 액션 전투의 완성형으로 판단하지 않는다.
Netcode for Entities 공식 문서는 예측과 서버 스냅샷으로부터의 재시뮬레이션을 설명하며 CPU 비용도 지적한다. [N2]
이 문서에서 인용한 패키지 버전은 동작 설명의 출처이고, Unity 6.3에 설치하기로 확정한 조합이 아니다.
M0의 호환성 확인과 M1 측정 결과로 실제 패키지 버전을 고정한다.
두 후보를 동시에 제품에 통합하지 않는다. 같은 진단 과제의 결과·제약·유지 비용을 비교해 하나를 선택한다.

## 6. 예측·보정의 최소 범위

로컬 영웅의 이동과 입력 접수 표현을 우선 예측한다. 타인의 확정 상태는 서버 스냅샷을 보간한다.
클라이언트는 입력 이력과 예측 상태를 보관하고 서버가 처리한 마지막 입력 번호를 받는다.
서버 기준 상태로 복원한 뒤 아직 승인되지 않은 자기 입력을 다시 적용하는 경로를 검증한다.
충돌·속박·밀치기가 개입한 상태를 저장할 수 없다면 단순 위치 보정만으로 해결했다고 기록하지 않는다.
예측한 시전의 VFX는 임시 식별자로 연결하고 거부·취소 시 정리하며 재실행 때 중복 생성하지 않는다.
피해 숫자·킬·경제 보상은 서버 확인 후 표시한다. 로컬 선행 표시가 필요하면 확정 표시와 구분한다.
과거 적 위치를 되감는 공격 판정 보상은 M1의 기본 기능에 넣지 않는다.
서버 현재 상태 판정의 체감이 불충분하면 M1에서 보상 범위와 공정성 규칙을 별도 결정한다.
계속되는 큰 보정은 시각적으로 숨기기만 하지 않고 원인·빈도·크기를 기록한다.

## 7. 물리와 시간의 주의점

고정 tick, 동일한 코드, 동일한 난수 seed만으로 기기 간 완전한 결정성을 가정하지 않는다.
Unity의 Enhanced Determinism도 actor 삽입 순서 조건과 성능 비용을 명시하므로 만능 동기화 옵션으로 취급하지 않는다. [N3]
영웅은 반경 0.45m의 접지 capsule을 기준으로 하고 높낮이는 초기 판정에서 장식으로 제한한다.
이동은 직접 제어하는 평면 운동·충돌 규칙부터 검증하고 ragdoll·강체 힘 누적을 핵심 판정에서 제외한다.
호스트와 원격 클라이언트의 충돌·시전 취소·CC 종료 tick 불일치는 별도로 추적한다.
기록 재생은 처음에는 서버 이벤트·스냅샷 진단용이며 입력만으로 모든 환경에서 완벽 재현된다고 약속하지 않는다.

## 8. M1 지연 시험 매트릭스

| 조건 | 공통 과제 | 기록 |
| --- | --- | --- |
| 50ms RTT, 손실 0% | 클릭 이동, 방향 전환, 이동 중 시전 | 입력→화면 반응, 위치 보정, 명중 지연 |
| 100ms RTT, 손실 0% | 근접 거리 진입·이탈, 벽 접촉 | 범위 경계 판정, host/remote 차이 |
| 150ms RTT, 손실 0% | 도주, 시전 취소, 연속 명령 | 체감 가능한 지연과 보정 원인 |
| 각 RTT + jitter ±20ms + 손실 1% | 같은 과제를 반복 | p50/p95/p99 보정량·메시지 지연 |
| 150ms RTT + 손실 3% | 상태 회복, 사망·리스폰 | 영구 불일치·중복 보상·정지 여부 |
| 연결 중단과 재연결 진단 | 손실 감지·오류 안내·재연결 가능성 확인 | 감지 시간과 상태 불일치; 실제 봇 인계/매치 복원은 M2 |

표의 RTT는 왕복 시간이다. 도구가 편도 지연을 입력받으면 절반 값을 적용하고 실측 RTT를 확인한다.
호스트 역할을 바꾸고 각 조건에서 두 컴퓨터의 독립 실행 빌드를 시험한다.
M1의 한 영웅 장면에서 자동 반복 가능한 이동·시전 사례를 만들고 실제 손 조작 영상을 함께 남긴다.
첫 통과 가설: 정상 이동의 입력→로컬 표현 p95 50ms 이내, 확정 명중·보상 중복 0건.
100ms RTT·손실 1%에서 일반 이동의 서버 대비 보정 거리 p95 0.25m 이하를 첫 조사 기준으로 둔다.
충돌·밀치기·리스폰은 일반 이동 표본과 분리하고 큰 보정의 원인을 개별 확인한다.
수치는 제품 성능 보증이 아니다. 결과를 본 뒤 근거와 함께 기준을 수정하거나 기술 경로를 바꾼다.
150ms 환경에서 조작감이 허용되지 않으면 지원 지역·매칭 RTT 정책을 결정하기 전 M1을 통과시키지 않는다.

## 9. M2의 실제 3v3 검증

- 세 영웅 종류로 구성한 플레이어 영웅 객체 6개와 세 라인의 웨이브·12개 타워·코어를 포함한 완전한 경기를 반복한다.
- 바스·리오·네마의 판정 형태, 일시 장치 제거, 귀환 타격의 중복 방지를 검사한다.
- 3초 창의 hard CC 1.5초 상한, 루트 중 시전, 스턴 중 입력 거부를 검사한다.
- 안개 속 적 객체의 불필요한 상태·음향·피격 피드백이 새어 나오지 않는지 확인한다.
- 서버 이벤트 로그로 경험치·크레딧의 소수 분배, 성장 한도, 막타 보너스를 대조한다.
- 한 라인의 타워 파괴 후 코어 노출, 미니언 부재 보호, 같은 tick 코어 파괴를 검사한다.
- 수동 플레이와 같은 명령 인터페이스를 사용하는 기본 봇으로 반복 부하를 재현한다.
- 연결 손실 5초의 봇 인계, 60초 복귀 경계, 사망 중 복귀, 단일 소유권과 전체 매치 상태 복원을 검증한다.

## 10. 방·재접속·호스트 이탈

M2의 비공개 방은 listen server로 시작한다. 호스트 PC가 권위 서버와 자기 클라이언트를 함께 실행한다.
계층은 화면 없는 전용 서버 실행으로 옮길 수 있게 두되 실제 전용 서버 호환은 별도 빌드로 증명한다.
연결 손실 5초 후 봇이 해당 영웅을 맡고 원래 사용자의 복귀 허용 시간은 손실 시점부터 60초다.
60초 안에 인증된 원래 사용자가 돌아오면 한 번에 소유권을 넘기고 봇 입력을 중단한다.
기한이 지나면 해당 플레이어의 재입장 권한을 종료하고 남은 경기는 봇이 계속 맡는 초기 정책으로 둔다.
낯선 사용자의 경기 중 빈자리 채우기는 제공하지 않는다.
사망 중 재접속은 부활을 앞당기지 않으며 쿨다운·성장·재화를 서버 상태로 복원한다.
테스트에서 호스트가 이탈하면 세션을 중단하고 승패 없음으로 안내한다. 자동 호스트 이전은 구현했다고 가정하지 않는다.
M4에는 출시용 호스트 이탈·서비스 장애·경기 중단 정책을 확정한다.

## 11. Steam과 호스팅의 역할

Steam 로비는 방 발견·초대·준비 상태를 다루며 실제 게임 전송과 권위 상태를 별도로 구성해야 한다. [N4]
Steam Datagram Relay는 통신을 중계하는 서비스로 P2P와 전용 서버 통신에 사용할 수 있다. [N5]
전용 서버의 실행 컴퓨팅은 별도 운영 대상이며 Steam 문서는 개발자 또는 커뮤니티 호스팅을 설명한다. [N6]
후보 바인딩과 전송 어댑터는 선택한 NGO·SDK·backend에서 연결·종료·재접속을 실측한다.
M1의 Unity Transport 직접 연결 성공은 Steam 초대·NAT 환경·Relay 연결의 성공 증거가 아니다.
공개 경쟁 환경에는 전용 서버를 우선 평가하되 M4의 공정성·지역·비용 근거로 최종 선택한다.
listen server 유지 시에는 호스트 신뢰와 이탈 한계를 공개 범위·게임 약속에 반영한다.

## 12. 성능·운영과 완료 증거

서버 tick 처리 시간의 p95/p99, 클라이언트 CPU/GPU 프레임 시간, 할당량, 객체 수, 전송량을 함께 기록한다.
30Hz의 한 tick 예산은 약 33.3ms다. 모든 예산을 쓰지 않도록 여유를 두고 M2 부하로 실제 한도를 정한다.
목표치만 보고 성공으로 기록하지 않고 측정 PC·빌드 hash·버전·RTT·손실·경기 시드를 붙인다.
M1 종료: 후보 선택과 예측 책임, 미해결 충돌·판정 제약을 기록한다.
M3 종료: 사람 6명이 완주한 경기와 읽기 쉬운 오류·재접속 안내를 확인한다.
M4 종료: 실제 지역 접속률, 호스트 우위, 전용 서버 월 견적을 비교한 운영 결정을 남긴다.
M5 종료: 출시 장비·빌드·Steam 경로에서 성능과 장애 복구를 확인한다.
