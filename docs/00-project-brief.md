# Project E 프로젝트 개요

- 버전/작성일: v0.2 / 2026-10-22
- 상태: 사용자 요구를 반영한 기획안. 아래 제안은 구현과 플레이테스트로 검증한다.
- 관련: [공통 규칙](01-core-rules.md), [로드맵](02-development-roadmap.md), [결정 이력](05-decisions-and-sources.md)

## 1. 한 줄 정의

**세 명이 세 라인을 관리하며 빠른 스킬 교전과 경기 중 능력치 투자를 반복하고, 짧은 지원 동선에서 얻은 우위로 상대 공명핵을 파괴하는 독립 PC 액션 AOS.**

작업명은 Project E다. 공개 게임명, 로고, 상표 검토 결과는 아직 정하지 않았다.

## 2. 확정된 사용자 요구

| ID | 요구 | 기획에 반영하는 방식 |
|---|---|---|
| U01 | 별도의 PC 게임 | 독립 실행 빌드와 온라인 대전을 설계 |
| U02 | Steam 출시 목표 | 출시 준비와 테스트 배포를 개발 로드맵에 포함 |
| U03 | 시티 오브 템페스트에서 느낀 게임성 유지 | 빠른 스킬 교환, 3대3/3라인, 성장 선택, 지원·공성 판단 유지 |
| U04 | 원작을 재현한 게임이라는 인상은 피함 | 새로운 영웅 기술 조합, 전장 배치, 세계관, 모델, 소리, UI |
| U05 | 콘텐츠·캐릭터 요소별 기획과 로드맵 | 분야별 문서, 제작 범위 표, 단계별 검증 기준 작성 |
| U06 | project-e 저장소에 문서 작성 | 문서를 저장소의 docs 아래에 정리 |
| U07 | Godot으로 진행 | Godot 기반 개발 환경과 실행 가능한 시작 프로젝트 구성 |

사용자가 “godot 으로 해보자”라고 선택했으므로 현재 엔진은 **Godot 4.7.2 Standard**다. 초기 구현 기본값은 **타입을 명시한 GDScript와 Compatibility 렌더러**이며, 언어와 렌더러까지 사용자가 직접 지정한 것은 아니다. Steam 출시가 특정 엔진을 요구하는 것은 아니다. 에디터는 `.godot-version`에 `4.7.2`로 고정하며 Linux에서 `4.7.2.stable.official.ed1daf0bf` 실행을 확인했다. 같은 버전의 export template과 Windows 실행은 별도 검증한다. 버전 고정과 선택 근거는 [Godot/Steam 기술 기준](technical/01-godot-and-steam.md), 시작 프로젝트의 실행·검증 범위는 [Godot 빠른 시작](technical/03-godot-quickstart.md)을 따른다.

시작 프로젝트 경로는 `game/project-e/project.godot`이다. M0 기반 소스와 오프라인 입력·이동·E의 선딜/돌진/후딜·자원/쿨타임 진단부터 구성한다. 이는 바스 전체 기술, 네트워크 대전 또는 M1 완료를 뜻하지 않는다. Windows 실행 파일·수동 조작·온라인 지연 검증은 해당 증거가 생길 때 별도로 기록한다.

## 3. 제작 가정과 제품 범위

- 최초 플랫폼은 Windows x86_64, 마우스·키보드다. Mac/Linux/Steam Deck/컨트롤러 지원은 별도 검증 후 결정한다.
- 소규모 제작을 가정하지만 실제 인원·예산·주당 작업 시간은 확인 전이다. 출시일을 확정하지 않는다.
- 한 판 목표 시간 12–18분은 테스트 가설이다. 시간 초과로 강제로 종료하지 않는다.
- 한국어를 우선 작성하고 출시 후보에서는 영어 UI/튜토리얼의 검수 경로를 마련한다.
- 기본 제품은 3대3 대전이다. 봇 연습과 비공개 방은 소수 인원으로도 테스트하고 즐길 수 있게 한다.
- 가격, 유료/무료 배포 방식, 운영 서버 예산은 M4 이후 실제 이용·운영 데이터를 보고 결정한다.

## 4. 유지할 재미와 새롭게 만들 경험

| 유지할 판단 | 신규 게임에서의 구현 원칙 |
|---|---|
| 공격·회피·재진입을 연속 판단 | 기술별 궤적, 선딜, 위험 구역과 대응법을 새로 설계 |
| 라인에 남기와 빠른 합류를 선택 | 세 라인을 짧은 연결 통로로 잇되 각 통로의 접근 각도와 시야가 다름 |
| 지금 필요한 성장에 투자 | 전투력·생존·기동·자원 회복에 직접 포인트 배분 |
| 파밍 우위를 전투와 공성으로 연결 | 병력·경험치 셀·타워·핵을 하나의 승리 흐름으로 연결 |
| 팀원의 강점을 활용 | 고정 탱커/힐러 의무 조합 없이 서로 다른 기술이 진입 기회를 만듦 |

영웅의 이름과 이펙트만 바꾸는 방식은 설계 기준에 맞지 않는다. 예를 들어 회수형 영웅은 자신의 이동으로 귀환 투사체의 경로를 바꾸고, 장악형 영웅은 제한된 두 장치의 연결선을 활용한다. 원작 영웅의 기술 목록을 대조표로 삼지 않는다.

장르적 유사성을 알아보는 플레이어가 있을 수 있다. 독립적인 정체성의 통과 기준은 플레이어가 이 게임의 고유한 연계·상대법·전장 장면을 설명할 수 있는지다. '아무도 영향을 떠올리지 않는다'는 보장으로 바꾸지 않는다.

## 5. 제안 세계관과 그래픽

### 공방 연맹의 수로 경기

물과 공명 에너지로 움직이는 공방 도시에서 길드들이 세 명의 조율사를 출전시켜 시설 제어 경기를 치른다. 상대 공명핵의 보호망을 해제하고 제어권을 확보하면 승리한다. 병력은 소형 작업 인형이고, 방어 시설은 공방 설비이며, 경험치 셀은 회수 가능한 시험용 에너지 장치다.

이 설정은 경기장과 기술에 맥락을 제공한다. 첫 제작에서는 짧은 소개 문구와 훈련 안내로 전달한다. 긴 캠페인, 분기 스토리, 대사 연출은 핵심 대전 검증 범위에 포함하지 않는다.

그래픽은 도자기·천·목재·구리 등의 재료를 활용한 밝은 스타일의 3D를 제안한다. 큰 실루엣과 뚜렷한 기술 궤적이 빠른 전투에서 읽히도록 한다. [상세 표현 기준](content/01-world-and-presentation.md).

## 6. 플레이 한 판의 흐름

1. 영웅과 팀을 선택하고 역할을 조율한다. 같은 팀의 영웅 중복은 막고 상대 팀과의 동일 영웅은 허용한다.
2. 기본기 3개와 초기 성장 포인트로 첫 라인에 진입한다.
3. 라인 병력과 경험치 셀을 처리하며 견제하고, 성장 포인트와 크레딧을 얻는다.
4. 능력치와 특수기 해금을 선택한다. 자원 회복·소모품 비용을 고려해 교전한다.
5. 옆 라인 지원, 상대 귀환 시간, 병력 위치를 이용해 방어 시설을 압박한다.
6. 한 라인의 외곽·내곽 방어탑을 파괴해 상대 공명핵을 노출시킨다.
7. 상대 핵을 파괴하면 경기가 끝난다. 결과 화면은 킬 수와 함께 공성·지원·성장을 보여준다.

## 7. 첫 프로토타입과 출시 후보

| 요소 | 실제 3대3 프로토타입 M2 | 출시 후보 M5 |
|---|---|---|
| 영웅 | 신규 3종 | 검증을 통과한 6종 후보 |
| 주력 맵 | 수로 공방 1개 | 동일 맵 1개를 완성 |
| 경기 | 성장부터 핵 파괴까지 한 판 | 접속·재접속·종료·신고 흐름까지 검증 |
| 봇 | 라인 전진과 기본 교전 | 연습에 유용한 난이도·불공정 정보 사용 검사 |
| 학습 | 최소 조작 안내 | 이동/기술/성장/지원/공성을 나눠 배우는 훈련 |
| 온라인 | 비공개 방 | 비공개 방 유지, 공개 매칭은 동접과 운영 조건 충족 시 |
| 표현 | 판정이 읽히는 임시 자산 | 영웅·맵·효과·소리·UI의 통일된 표현 |

첫 3종은 밸런스 전체를 입증하는 출시 영웅 수가 아니다. 신규 영웅 제작을 확대하기 전에 6명이 함께 플레이했을 때 재미와 읽기 쉬움이 성립해야 한다.

## 8. 성공 기준

- 짧은 기술 주기가 실제 공격·회피·재배치의 반복으로 이어진다.
- 합류가 빠르지만 라인을 비우는 손실도 있어 상황에 따른 선택이 생긴다.
- 성장 투자 차이를 플레이어가 설명하고 전투 결과에서 확인할 수 있다.
- 원작 지식 없이 각 영웅의 강점과 대응법을 학습할 수 있다.
- 6인 온라인에서도 이동·명중·피격의 결과를 신뢰할 수 있다.
- Steam 출시 후보는 재미, 기술, 운영, 배포 준비를 각각 통과한다.

정량 지표와 통과 방법은 [플레이테스트 문서](04-playtest-and-balance.md)에 둔다. 테스트 없이 '완성', '원활', '밸런스 확보'로 기록하지 않는다.
