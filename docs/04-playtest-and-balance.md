# 플레이테스트·밸런스·완성도 검증

- 버전/작성일: v0.1 / 2026-10-21
- 상태: 앞으로 실행할 검증 계획. 아래 수치는 관측 가설이며 실제 측정 결과가 아니다.
- 관련: [공통 규칙](01-core-rules.md), [로드맵](02-development-roadmap.md), [영웅](characters/README.md), [네트워크](technical/02-architecture-and-networking.md)

## 1. 검증할 다섯 가지

| 검증 축 | 질문 | 판단에 필요한 증거 |
|---|---|---|
| 전투 | 입력·명중·회피·재진입을 믿고 결정할 수 있는가? | 입력/서버 로그, 플레이 영상, 피격 설명 |
| 세 라인 | 파밍을 유지하거나 지원하는 선택에 각각 이유가 있는가? | 이동 경로, 라인 손실, 교전·공성 결과 |
| 성장 | 투자에 따라 원하는 방식으로 싸울 수 있는가? | 투자 시점·이유, 레벨별 결과, 소모품 사용 |
| 정체성 | 고유한 기술과 대응법이 새 경험을 만드는가? | 유도하지 않은 인터뷰, 다른 방식의 실제 조작 |
| 제품 | 처음 온 사용자가 접속·학습·완주·재경기할 수 있는가? | 설치/접속/학습/종료 기록과 실패 이유 |

그래픽이 다르다는 평가만으로 독립적인 게임성이 입증되지는 않는다. 재미에 대한 긍정 답변도 판정 오류·진행 불가·특정 조합의 강제를 상쇄하지 않는다.

## 2. 테스트 단계와 표본

| 단계 | 참가 구성 | 조사 단위 | 목표 |
|---|---|---|---|
| M1 | 개발자·내부 시험자, 두 클라이언트 | 같은 입력을 반복하는 재현 사례 | 판정·반응·보정의 원인 구분 |
| M2 | 사람과 봇 혼합 후 실제 6인 | 완주한 경기와 실패한 세션 모두 | 경기 규칙과 3라인 선택 확인 |
| M3 | 가능하면 참고작 경험자 6명·비경험자 6명 이상 | 최소 12회의 실제 6인 경기와 개별 인터뷰를 초기 모집 목표로 제안 | 정체성·학습·교전 가독성 탐색 |
| M4 | 여러 지역/환경의 외부 참가자 | 예약 세션·반복 방문·접속 실패 포함 | 운영 방식·큐 수요·출시 범위 판단 |
| M5 | 출시 대상 장비와 실제 배포 경로 | 고정된 출시 후보 빌드 | 회귀·성능·배포·오류 복구 검증 |

M3의 인원·경기 수는 탐색 연구의 모집 목표다. 모집이 부족하면 실제 수를 그대로 기록하고 관찰하지 못한 조합을 명시한다. 12경기를 했다는 사실만으로 전체 밸런스나 수요가 통계적으로 검증되었다고 쓰지 않는다. 친구·개발자·외부 신규 참가자를 구분한다.

## 3. 모든 기록에 필요한 정보

빌드 commit, 콘텐츠/프로토콜 버전, 일시, 영웅 조합, 플레이어 숙련도와 파티 여부, PC 사양, 화면 설정, 연결 지역·RTT·손실률, 호스트 여부를 기록한다. 매치 식별자는 개인 이름 대신 가명 ID를 사용한다.

경기 결과와 함께 정상 종료/중단, 실제 사람/봇 수, 연결 손실, 핵 노출·파괴 시간, 레벨/투자 이력, 피해·보상 이벤트를 남긴다. 실명·음성 원본 등의 수집은 기본값으로 요구하지 않는다. 실제 운영 전 수집 항목·보유 기간·접근 담당을 정한다.

## 4. 핵심 게임성 지표

| 항목 | 초기 가설·측정 방식 | 결과가 나쁠 때 확인할 것 |
|---|---|---|
| 경기 시간 | 사람 6인의 정상 경기 중앙값 12–18분을 목표로 관측; p90도 기록 | 이동/웨이브/탑 보호/성장/부활 중 지연 원인 |
| 인접 라인 합류 | 설계된 연결 통로 진입점→출구 약 3.5–3.8초, 전투 위치까지의 실제 시간은 별도 | 시작 위치·벽 우회·방해가 지원을 과도하게 지연하는지 |
| 시전 빈도 | 일반기 2–6초, 특수기 12–20초의 설계가 실제 사용 빈도로 이어지는지 | 에너지 고갈·과한 후딜·입력 부담·무의미한 난사 |
| 라인 유지/지원 | 지원 성공·실패, 빈 라인의 잃은 XP/탑 HP, 합류 후 복귀 경로 기록 | 전원 뭉치기 또는 영구 1대1만 유리한지 |
| 성장 선택 | 영웅·레벨별 투자와 플레이어가 말한 이유를 함께 기록 | 특정 한 항목만 필수인지, 선택 효과를 느끼는지 |
| 소모품 | 구매/보유/사용, 기지 복귀, 남은 크레딧의 분포 | 자원이 무의미하게 쌓이거나 회복이 교전을 무력화하는지 |
| 눈덩이 효과 | 첫 처치·첫 탑·레벨 차이와 최종 결과의 관계 | 경험치 분배·파밍 차단·죽음 대기·공성 보호 |
| 고유한 경험 | 바스/리오/네마의 다른 의사결정과 상대법을 설명하는지 | 이름·외형만 다르고 실질적인 조작은 같은지 |

맵의 3.5–3.8초는 초기 이동속도와 설계 좌표에서 계산한 통로 이동 시간이다. 클릭 반응·접근 거리·전투 방해를 포함한 실측 합류 시간과 혼동하지 않는다. 경기 목표 범위를 벗어나면 원인을 분석하며 타이머로 강제 종료해 지표만 맞추지 않는다.

## 5. 전투 수치 확인 방법

### 비교 조건

1. 레벨 1, 레벨 6, 레벨 12의 동일 투자 조건에서 피해·생존·에너지 소모를 비교한다.
2. 공격 투자, 생존 투자, 자원/기동 투자라는 대표 선택을 만들되 같은 사용 포인트 수로 비교한다.
3. R 해금 여부를 통제한다. R을 배운 쪽과 배우지 않은 쪽을 같은 빌드라고 취급하지 않는다.
4. 1대1 교환, 2대1 합류, 3대3 집중 공격, 탑 앞 교전, 좁은 통로를 나눠 관측한다.
5. 무입력 더미의 최대 피해와 실제로 회피/장치 파괴/이탈하는 상대의 피해를 분리한다.

### 함께 볼 결과

- 첫 피해부터 사망까지 시간, 실제로 행동할 수 있었던 시간, 회피 가능한 경고 시간.
- 기술을 모두 쓴 뒤 남은 에너지와 다음 유효 행동까지 기다린 시간.
- 방어/보호막과 성장 격차가 한 번의 작은 실수를 과도한 확정 사망으로 바꾸는지.
- 상대가 기술을 알았을 때도 대응할 방법이 없거나, 반대로 읽히면 아무것도 못 하는 영웅인지.
- 처치 수 외에 타워 압박, 길 막기, 장치 파괴, 아군 생존에 기여하는 정도.

한 영웅의 승률만 보고 상향/하향하지 않는다. 팀 내 중복 금지, 상대 미러 허용, 파티 숙련도, 조합과 표본 수를 같이 확인한다. 작은 표본의 50%에서 벗어났다는 이유만으로 밸런스 실패를 선언하지 않는다.

## 6. 반드시 재현할 규칙 경계

| 범주 | 사례 | 기대 판정 |
|---|---|---|
| 행동 | 에너지 부족·사거리 밖·시야 밖 대상·시전 중단 | 실패 승인에는 무소모, 승인 후 취소에는 환급 없음 |
| 다단 피해 | 같은 투사체/장치가 프레임마다 충돌, 대상 재진입 | 문서의 단계별 상한만 피해 적용 |
| 군중 제어 | 여러 영웅의 기절/속박/밀치기 연쇄 | 최근 3초 안의 합집합 조작 불가 시간 최대 1.5초 |
| 성장 | 최대 레벨·투자 상한·시전 중 투자·중복 명령 | 13포인트 총량, 상한 적용, 이미 발사한 위력 불변 |
| 보상 | 근처 0/1/2/3명, 사망한 투사체 소유자, 동시에 막타 | 근처 분배와 막타 보너스를 구분, 한 처치만 확정 |
| 소모품 | 최대 자원·사망·동시 사용·적 영웅 피해 | 잘못된 소비/중복 회복 없음, 공유 쿨타임 유지 |
| 시야 | 벽 뒤 장치/영웅, 안 보이는 적에게 지점 기술 적중 | 숨은 HP·정확한 위치·적중 정보를 화면/소리로 전달하지 않음 |
| 공성 | 잠긴 내곽 탑·병력 없는 공격·소환물만 존재 | 잠금/30% 보호/영웅 0.5배의 적용 구분 |
| 종료 | 같은 틱 양 핵 파괴·종료 뒤 투사체·재접속 | 무승부 또는 확정 결과 한 번, 추가 보상 없음 |
| 접속 | 5초 봇 인계·60초 복귀·기한 경계·호스트 종료 | 단일 제어권, 슬롯 정책, 정확한 중단 표시 |

서버 틱 경계의 시간은 구현 시 동일한 규칙으로 양자화한다. 문서의 0.1초 같은 시간이 프레임 수에 따라 다른 지속 시간이 되지 않게 한다.

## 7. 온라인과 성능

### M1 연결 조건

RTT 50/100/150ms, 패킷 손실 0%/1% 조건을 명시적으로 구성하고 같은 이동·기술 사례를 실행한다. 지터·재정렬이 포함되면 설정을 따로 기록한다. 서버와 호스트 플레이어의 유리한 환경을 원격 클라이언트 성능으로 보고하지 않는다.

| 지표 | 초기 조사 기준 | 해석 |
|---|---|---|
| 입력→로컬 표현 | 정상 입력 p95 50ms 이하 | 서버 명중 확정 시간과 다른 지표 |
| 일반 이동 보정 거리 | 100ms RTT·손실 1%에서 p95 0.25m 이하 | 벽 충돌·강제 이동·부활 표본은 따로 기록 |
| 판정/자원 무결성 | 재현 사례에서 중복 피해·중복 소비·중복 보상 0건 | 전체 서비스의 오류율 0을 보장하는 결과가 아님 |
| 서버 주기 | 30Hz 목표, 한 틱 약 33.3ms 예산 | p95/p99와 연속 초과·누적 지연을 함께 관측 |
| 화면 성능 | 60fps 목표, 1080p 낮음 설정의 후보 최소 장비 | 평균뿐 아니라 프레임 시간 p95/p99와 멈춤 기록 |

M2에서는 플레이어 객체 6개, 세 라인의 병력, 장치와 다단 기술, 시야 계산을 함께 올려 측정한다. 영웅 종류 여섯 종을 구현해야 이 부하 시험을 시작할 수 있는 것은 아니다. 실제로 검증하기 전에는 최소 CPU/GPU 모델을 확정하지 않는다.

긴 경기의 객체 잔류, 재경기의 초기화, 접속 손실을 포함한 연속 세션을 확인한다. 부하 목표는 실제 한 판의 최악 장면에서 출발하며 근거 없는 대규모 동접 수치를 제품 약속으로 사용하지 않는다.

## 8. 원작을 연상시키는 정도와 독립성 검증

처음에는 참고 게임 이름을 질문에 넣지 않는다. 동일 장르 경험을 배경 정보로만 받아 두고 플레이 직후 각자 답하게 한다.

### 질문

1. 이 게임에서 가장 재미있었던 장면과 가장 답답했던 장면은 무엇이었나?
2. 방금 고른 영웅은 어떤 상황을 만들 때 강하고, 상대는 무엇으로 막을 수 있었나?
3. 라인을 떠나 지원한 이유 또는 남아 있던 이유는 무엇이었나?
4. 투자 항목을 바꾸고 싶었던 순간은 언제였나?
5. 다음 판에 해보고 싶은 다른 선택은 무엇인가?

이후 참고작 경험자에게만 어떤 게임을 떠올렸는지, 그 이유가 장르/속도/기술 구조/맵/화면 중 무엇이었는지 묻는다. 단순히 장르가 비슷하다는 답과 특정 영웅·맵의 일대일 재현으로 읽힌다는 답을 구분한다.

### 재설계 신호

- 참가자가 새 캐릭터를 특정 원작 영웅의 이름으로만 설명하고 새 상대법을 말하지 못한다.
- 리오의 이동 경로, 네마의 장치 위치, 바스의 공격 지연이 실제 의사결정에 영향을 주지 않는다.
- 외형을 가린 회색 도형 상태에서 영웅별 조작과 대응이 거의 구분되지 않는다.
- 그래픽 반응은 좋지만 지원·성장·공성에 대한 재플레이 이유가 없다.

이런 신호가 반복되면 기술의 상호작용과 맵의 결정 구조를 고친다. 이름이나 색상만 바꾸는 수정으로 독립성 문제를 완료 처리하지 않는다. 모든 이용자가 참고작을 떠올리지 않는다는 보장은 목표로 삼지 않는다.

## 9. 신규 사용자 학습

훈련 후 이동/공격, 위험 구역 회피, 성장 투자, 미니맵을 보고 인접 라인 지원, 병력과 함께 보호된 구조물 공격이라는 다섯 과제를 제시한다. 초기 목표는 도움 없이 5개 중 4개 이상 수행하는 것으로 두되 영웅과 입력 장치, 실패 원인을 기록한다.

다시 배우기, 건너뛰기, 키 변경 후 재안내를 확인한다. 텍스트를 끝까지 읽었는지보다 실제로 행동할 수 있는지를 본다. 적/아군 구별과 위험 표시는 색상 외의 모양·외곽선·소리로도 확인한다.

초보자 모드가 감춰진 능력치 우위를 주거나 봇이 보이지 않는 상대 정보를 이용하면 학습 결과가 실제 대전과 달라진다. 봇 난이도는 입력 속도와 선택 수준으로 조정하고 동일 시야·자원·명령 제한을 유지한다.

## 10. 외부 테스트와 공개 매칭

지역·시간대별 실제 사람 6인 경기 성립률, 대기 p50/p95, 연결 성공, 이탈, 재방문을 관측한다. 첫 조사 기준은 예약 시간대의 경기 성립률 90% 이상과 대기 p95 120초 이하로 제안한다. [출시 계획](release/01-steam-release-plan.md)과 동일한 가설이다.

경기 성립률의 분모는 해당 세션에서 매칭 참가를 시도한 적격 사용자/파티의 시도로 정의하고 취소·실패·시간 초과를 따로 보고한다. 성공한 경기만 추려 분모를 만들지 않는다. 중복 클릭/재시도는 같은 시도로 묶는 기준을 고정한다. 봇으로 채운 경기와 미리 짠 친구 경기의 비중은 따로 표시한다.

예약 시간대 결과를 상시 공개 큐의 가능성으로 바로 환산하지 않는다. 자연 유입, 시간 분산, 지역별 지연, 파티 구성을 확인한 뒤 공개 큐 여부를 결정한다. 기준 미달은 콘텐츠 추가만으로 해결하려 하지 않고 모집 시간대·운영 형태·제품 범위를 함께 검토한다.

## 11. 관측 기록 양식

다음 항목을 실제 테스트마다 채운다. 현재 실행된 테스트 결과는 없다.

| 기록 항목 | 적을 내용 |
|---|---|
| 식별 | 세션 ID, 날짜, 빌드 commit, 규칙/콘텐츠 버전 |
| 가설 | 이번 세션에서 확인하려는 질문 하나와 비교 조건 |
| 참가/환경 | 사람·봇 수, 숙련도, PC, 지역, RTT/손실, 호스트 |
| 관측 | 경기별 수치, 실패 사례, 타임스탬프, 직접 관찰한 행동 |
| 참가자 설명 | 유도하지 않은 답변과 관측을 분리 |
| 판정 | 통과/재설계/표본 부족, 그 이유 |
| 후속 작업 | 바꿀 변수, 관련 문서/데이터, 재확인 조건 |

한 번에 여러 변수를 바꾸면 무엇이 결과를 바꿨는지 알기 어렵다. 원인을 좁힐 때는 영향이 큰 변수부터 작은 변경으로 확인한다. 진행 불가·악용·데이터 손상이 확인되면 다음 모집 전에 우선 고친다.

## 12. 자동화와 사람 검증의 역할

자동 검증은 피해/성장/보상/접속/종료처럼 같은 입력에 같은 판정이 필요한 경계에 우선 적용한다. 플레이 감각·가독성·고유한 재미는 사람이 실제 대전에서 확인한다. 기획 숫자를 그대로 다시 적은 검사만 통과시켜 제품 완성의 증거로 삼지 않는다.

문서 작성 단계의 링크·수치·범위 일치 확인과 게임 빌드의 테스트를 구분한다. 이 저장소의 현재 상태는 전자이며, 게임이 재미있거나 60fps로 작동한다는 실측 증거는 후속 개발에서 확보한다.
